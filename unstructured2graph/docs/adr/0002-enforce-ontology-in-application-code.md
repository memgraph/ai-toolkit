# Enforce the entity-type ontology in application code, not Memgraph or LightRAG

Neither Memgraph nor LightRAG can enforce a closed entity-type vocabulary on our behalf. Memgraph's constraint system has no value-membership constraint (`ASSERT n.prop IN [...]` isn't valid Cypher), and labels are always freely assignable regardless of any constraint in place. Memgraph does have real `CREATE ENUM` support that rejects out-of-vocabulary values at write time — verified live — but only for writes that use the explicit `EnumName::Value` cast syntax; a plain string property (what LightRAG writes) bypasses it entirely, and evolving the vocabulary is one-directional in the current version (`ALTER ENUM ... ADD VALUE` works, `REMOVE VALUE`/`DROP ENUM` are both "Not yet implemented"). LightRAG's own `entity_types_guidance` is just prompt text, with no code-level check against what the LLM actually returns. Enforcement therefore lives entirely in `unstructured2graph`'s own Python code (`promote_entity_types_to_labels`), with an existence + `IS TYPED STRING` constraint on `entity_type` as the only (weak) Memgraph-level backstop.

**Considered**: Memgraph `CREATE ENUM` as a stronger backstop — rejected due to the cast-syntax requirement (LightRAG never casts, so it wouldn't engage) and the missing removal/drop support. May be worth revisiting once Memgraph's enum feature matures.
