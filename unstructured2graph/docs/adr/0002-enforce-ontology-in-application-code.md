# Enforce the entity-type ontology in application code, not Memgraph or the extraction backend

Neither Memgraph nor any `ExtractionBackend` can enforce a closed entity-type vocabulary for us. Memgraph's constraint system has no value-membership constraint (`ASSERT n.prop IN [...]` invalid Cypher); labels always freely assignable regardless of constraints. Memgraph's `CREATE ENUM` does reject out-of-vocabulary values at write time — verified live — but only for writes using explicit `EnumName::Value` cast syntax; a plain string property (what every backend writes — LightRAG's free-form LLM output, GLiNER2's closed-vocabulary label) bypasses it entirely, and vocabulary evolution is one-directional today (`ALTER ENUM ... ADD VALUE` works, `REMOVE VALUE`/`DROP ENUM` both "Not yet implemented"). LightRAG's own `entity_types_guidance` is just prompt text, no code-level check against what the LLM returns — and even GLiNER2's closed schema is enforced by the model's inference, not by Memgraph. Enforcement lives entirely in `unstructured2graph`'s own Python code (`promote_entity_types_to_labels`), with an existence + `IS TYPED STRING` constraint on `entity_type` as the only (weak) Memgraph-level backstop.

**Considered**: Memgraph `CREATE ENUM` as stronger backstop — rejected: cast-syntax requirement (no backend casts, wouldn't engage) + missing removal/drop support. Revisit once Memgraph's enum feature matures.
