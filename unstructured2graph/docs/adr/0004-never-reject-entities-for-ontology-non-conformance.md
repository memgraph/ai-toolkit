# Never reject entities for failing ontology conformance

The obvious design would filter or reject entities whose entity_type doesn't match the ontology. We deliberately don't. LightRAG's own KV/vector/doc-status stores key off the same entity_id and expect the graph node to keep existing, so deleting a node post-hoc would desync LightRAG's internal bookkeeping. More fundamentally, the ontology is expected to evolve — treating it as a lens rather than a filter means the raw entity_type signal is always preserved, so a later change to the ontology can retroactively promote labels for entities that didn't conform under an older version, without re-running extraction. Non-conforming entities are instead stamped `ontology_conformant: false`: kept, visible, and queryable, rather than silently dropped or indistinguishable from a node that was never processed.

**Considered**: rejecting/deleting non-conforming entities outright — rejected due to the LightRAG storage-consistency risk above, and because it would destroy the raw signal needed for future re-projection.
