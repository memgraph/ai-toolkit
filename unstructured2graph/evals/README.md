# Extraction backend eval: GLiNER2 vs LightRAG

Answers one question directly: given the same text, how do `LightRAGBackend`
and `GLiNER2Backend` compare on entity/relation extraction quality, latency,
and cost? Deliberately *not* an LLM-judged eval like `context-graph-eval` --
entity/relation matching against gold spans is a countable metric
(precision/recall/F1), and asking a judge to grade a number you can count
adds variance for no information. The one real source of run-to-run noise is
LightRAG's own LLM extraction; GLiNER2 is a fixed model with no sampling, so
repeat its runs too (`--repeat`) before trusting any delta between the two.

This does **not** answer "does swapping the backend hurt real memory
recall?" -- that needs the full `sessions-graph` reconcile → retrieve → score
pipeline `context-graph-eval` already owns, which is not wired up to
`GLiNER2Backend` (`sessions_graph.reconcile_session`'s `lightrag_wrapper`
param is still LightRAG-specific). Deliberately deferred: see #330's PR
description and the design note this eval's PR links.

## Running it

Needs a live, **dedicated** Memgraph instance -- wiped before each backend's
pass, so never point this at a shared or development database:

```bash
docker run -d --name ai-toolkit-eval-memgraph-extraction -p 7691:7687 \
    memgraph/memgraph-mage:latest
```

```bash
# both backends, one pass each
uv run --package unstructured2graph python evals/extraction_quality.py

# just one backend, repeated 3x to see its own variance
uv run --package unstructured2graph python evals/extraction_quality.py --backend lightrag --repeat 3
```

`lightrag` needs `OPENAI_API_KEY` (or another configured LLM); `gliner2`
needs `pip install 'gliner2[local]>=2.0.0'` installed manually (not a
`pyproject.toml` extra -- see `gliner2_backend.py`'s module docstring for
why). Either backend is skipped with a clear message, not a hard failure,
if its dependency is missing -- mirrors the package's own
`test_e2e_lightrag.py`/`test_e2e_gliner2.py` opt-in-and-skip convention.

`main()` auto-loads a `.env` file if `python-dotenv` is installed (it's in
the `test` extra: `pip install -e ".[test]"`) -- a bare `load_dotenv()` call,
so it finds the repo-root `.env` via its own upward search regardless of
whether you run this from `unstructured2graph/` or the repo root. Without
`python-dotenv` installed, export `OPENAI_API_KEY` yourself before running.

## The gold corpus

`gold_corpus.jsonl` is generated by `build_gold_corpus.py`, not hand-typed --
run the script again after editing its `LONGMEMEVAL_RECORDS`/
`AUTHORED_RECORDS` lists to regenerate it. Two provenances, kept visible on
every record and never blended silently (mirrors `context-graph-eval`'s own
Tier 1/Tier 2 split):

- `longmemeval`: real conversational turns, hand-picked from
  `context-graph/eval/corpus/tier1-longmemeval.jsonl`. Entity-rich, but this
  natural chat corpus carries almost no explicit named-entity-to-named-entity
  relations (verified: zero matches for "works at/for|founder|founded|
  CEO|professor at|based in|headquartered" across the whole corpus). Its
  relation coverage here is limited to two clear `located_in` statements.
- `authored`: written for this eval specifically to exercise `works_for`/
  `founded`/`located_in` relation scoring, which the adopted text does not
  naturally contain. Fictional names/companies throughout.

**LLM-assisted, human-reviewed, not gospel.** Entity/relation spans were
drafted with model assistance and checked by hand against
`default_ontology.yaml`'s vocabulary before being committed, but treat this
as a solid first draft -- spot-check it, especially before anyone leans on a
single number it produces to make a real decision.

**Gold is salient-entity coverage, not exhaustive annotation** -- each chunk
is only marked up with the handful of clearly-named entities a human would
call out, not every noun phrase the broad `default_ontology.yaml` vocabulary
(`Concept`, `Event`, `Artifact`, `Method`... deliberately wide categories)
could arguably cover. Verified live against GLiNER2's real output: given
"...a lecture at the History Museum about ancient civilizations...", it
correctly found the gold `History Museum`, `Jordan`, `Petra` *and* also
tagged `lecture` (Event), `history` (Concept), `significance` (Concept) --
defensible under the ontology's own definitions, but not in gold, so they
count as false positives. **This structurally understates precision** for
any backend that extracts more exhaustively than this gold set does --
`ent R`/`rel R` (did it find what gold marked) are the more trustworthy
numbers here; `ent P`/`rel P` are a floor, not a measured ceiling. A real
before/after comparison (e.g. narrowing the ontology, or a more exhaustive
gold annotation pass) should account for this rather than reading precision
at face value.

## Reading the report

- **`ent P/R/F1`** -- entity matching by normalized text only, type ignored:
  "did it find the right things." Uses the same normalization
  (`gliner2_backend._normalize_text`) on both backends' output so they're
  compared on the same basis.
- **`typed P/R/F1`** -- entity matching by normalized text *and* type
  (case-folded, since LightRAG's raw `entity_type` casing is whatever its
  LLM returned): "did it classify them right." Harder to compare apples to
  apples than the type-agnostic number, since LightRAG's types are
  LLM-assigned free text and GLiNER2's come from a closed schema.
- **`rel P/R/F1`** -- relation triples (`type`, `head`, `tail`) by normalized
  text. **Only meaningful for GLiNER2** here: LightRAG has no
  `Ontology.relation_types` concept, writes generic `:DIRECTED` edges with no
  typed label to score against, and is reported `n/a` rather than a
  misleading zero.
- **`ontology_conformant`** -- a free bonus signal from running with
  `enforce_ontology=True`: what fraction of extracted entities matched
  `default_ontology.yaml`'s vocabulary at all, independent of gold.
- **`calls` / `cost`** -- LightRAG only (`n/a` for GLiNER2 -- zero LLM calls,
  not merely "$0", is itself the headline). The per-row detail line under each
  backend prints the prompt/completion token split and which model priced it.
  Both token counts and dollar cost are *approximate*: tiktoken's `cl100k_base`
  over prompt/completion text (LightRAG's `llm_model_func` returns a plain
  string, not a response object with native usage stats), times a pinned,
  point-in-time price per model in `MODEL_PRICING_PER_1M_TOKENS` -- not
  provider-billed usage. A model missing from that table reports `unpriced`,
  never a silent `$0`.

No automatic verdict, on purpose -- this tool's job is to make the comparison
legible, not decide for anyone (mirrors `context-graph-eval`'s "promotion is
human-gated" stance).
